# Автоматическая приёмка

Цель — автоматически проверять каждое включённое требование и риск изменённого поведения. Число тестов и процент покрытия сами по себе не подтверждают корректность. Задача содержит таблицу `AC → тест → результат`; для непроверяемого здесь пункта указываются причина, владелец и оставшийся способ проверки.

| Изменение | Автоматические проверки |
| --- | --- |
| Domain/правило | Границы, invalid input, каждый исход правила; regression для исправленного бага |
| ViewModel | UiState, success/empty/error/retry/cancel, двойное действие, поздний ответ, restoration |
| HTTP/mapper | Реальный parser + MockWebServer, schema/null/204/errors, pagination, cookies/cancel |
| Room/storage | Реальный adapter, account isolation, миграции и очистка |
| Compose | Semantics, navigation, loading/error/empty, доступность, screenshot diff |
| Media/security | Lifecycle, provider/permissions, recorder, Keystore; instrumentation/device сценарии |
| Общий контракт | Все потребители, Fake/real, DI и обе demo/prod сборки |
| Документы/инструменты | Ссылки, privacy, metadata skills, тесты изменённых скриптов |

Тесты не зависят от живого интернета, реального времени и личных данных. Использовать управляемые dispatcher/clock и синтетические fixtures. Изменённый баг воспроизводится до исправления, когда это возможно. Не тестировать приватные детали вместо наблюдаемого результата. Не добавлять бессмысленные тесты на getters ради процента.

## Политика покрытия после scaffold

Dev 2 настраивает совместимый инструмент покрытия после проверки зависимостей. Стартовая политика проекта: **не менее 85% строк и 80% ветвей для hand-written domain/data/ViewModel**, без снижения существующего покрытия. Для каждого изменённого бизнес-правила и обработчика ошибки нужен сценарий независимо от общего процента. Сгенерированный код, декларативный DI и preview исключаются явно; production logic, сложные ветви и неудобные классы исключать нельзя. Compose проверяется поведенчески и screenshot-тестами, а не только line coverage. Если выбранный инструмент не умеет достоверно считать branch coverage, gate остаётся незавершённым до выбора поддерживаемого решения, а метрика не объявляется выполненной.

Новые screenshot baselines впервые просматриваются глазами. Последующие изменения автоматически сравниваются; agent проверяет diff, не принимает новую базу только ради зелёного CI. Для аппаратных свойств и live CAPTCHA остаются целевые проверки, которые нельзя честно заменить mock. Ручное ревью желательно, но не является обязательным условием выполнения задачи в этой части проекта.

## Единая команда

```text
python scripts/quality_gate.py
python scripts/quality_gate.py --scope repository
python scripts/quality_gate.py --scope android
python scripts/quality_gate.py --scope android --ui
```

Автовыбор включает Android gate, если появился wrapper или Kotlin/Java source вне игнорируемых каталогов. Repository scope проверяет только пакет документов/инструментов и всегда так помечается. Android scope без scaffold или настройки возвращает ошибку, не зелёный результат. Перед первым запуском тестов extractor установить его зависимости через `npm ci --prefix tools/design --ignore-scripts`.

`config/quality-gate.json` сейчас содержит пустой Android-раздел: приложение ещё не создано. Dev 1/2 обязаны заполнить реальные команды после проверки Gradle tasks и добавить Android job с SDK/JDK в CI. Обязательные группы: format, static, architecture, unit, coverage, build-demo, build-prod. Для UI — дополнительно ui. В `junit_reports` указать glob-пути результатов JVM/instrumentation tests; при `--ui` также задать `ui_junit_reports`. Gate требует ненулевое число выполненных тестов и отсутствие failures/errors. JUnit XML должны быть созданы текущим запуском: настройте test commands с --rerun-tasks, чтобы старый UP-TO-DATE отчёт не выдавался за новую проверку. Coverage task должна сама завершаться ненулевым кодом при нарушении порогов. Нельзя подставлять echo или команду, ничего не проверяющую.

Формат записи команды: `{"group":"unit","argv":["gradlew",":feature:library:testProdDebugUnitTest"]}` — это иллюстрация формата, имя задачи требуется проверить. `gradlew` runner заменяет на платформенный wrapper. Команды передаются аргументами, без shell-строк. Отчёт каждого запуска сохраняется только в `.local/quality/last-run.json`; он содержит scope, exit codes и статус, не доказывает состояние другого commit. CI публикует обезличенные отчёты actual tasks; наличие workflow ещё не означает, что он запускался.

## Внедрение в D1–D3

Dev 1 создаёт компилируемый эталон MVVM, варианты и toolchain. Dev 2 добавляет formatter/static analysis, тестовые зависимости, coverage verification и проверки архитектуры, заполняет gate, подключает CI. Оба проверяют намеренно нарушенный import/тест/порог: job должен стать красным, после удаления контрольного нарушения — зелёным. До этого Android quality gates считаются не настроенными. Прочие разработчики используют тот же эталон и дополняют автоматизированные сценарии своих задач.
