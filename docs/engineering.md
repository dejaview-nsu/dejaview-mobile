# Архитектура и качество кода

Обязательный подход проекта — **MVVM для presentation и Clean Architecture для границ зависимостей**. Это командное решение; оно не требует класса на каждый метод или Gradle-модуля на каждый слой.

| Слой | Ответственность | Допустимые зависимости |
| --- | --- | --- |
| presentation | Compose Content, route, ViewModel, UiState | domain, core/ui, платформенный UI |
| domain | Правила, модели, интерфейсы потребителей | Kotlin, coroutines/Flow, общие domain contracts |
| data | Repository implementation, DTO, mapper, HTTP/Room | domain, сетевые/платформенные adapters |
| di/app | Создание и связывание реализаций | Все нужные реализации, без бизнес-правил |

Пример: `MovieContent(state, onAction)` рисует состояние, `MovieRoute` собирает его с учётом lifecycle, `MovieViewModel` вызывает `PersonalMoviesRepository`. Реализация repository обращается к HTTP и отображает DTO в domain. ViewModel не получает Retrofit, DAO, Activity или NavController. `MutableStateFlow` остаётся приватным, наружу — `StateFlow`. Однонаправленный поток состояния совместим с MVVM и не означает переход на другой архитектурный паттерн.

Domain не импортирует Android, Compose, Room или Retrofit. Feature не импортирует implementation другой feature: взаимодействие через core contracts/routes/search-api. App выполняет wiring. Проверка графа должна анализировать фактические Gradle dependencies, включая транзитивные зависимости, а не только искать строки import. Проверку импортов domain добавить статическим правилом после появления package namespace.

SOLID применяется практически: одна ответственность на компонент; расширение через существующую границу при реальной необходимости; Fake сохраняет семантику настоящего интерфейса; интерфейсы узкие и ориентированы на потребителя; зависимости передаются конструктором. Не создавать универсальные BaseViewModel/BaseRepository, сервис-локатор, глобальный event bus или интерфейс для каждого класса. DRY не требует объединять похожий текст с разной предметной семантикой; KISS/YAGNI исключают преждевременные платформы и абстракции.

Стиль Kotlin следует [официальным conventions](https://kotlinlang.org/docs/coding-conventions.html), форматирование фиксируется одним выбранным инструментом. Небольшие функции, говорящие имена и минимальная видимость предпочтительнее сложных цепочек scope functions. Комментарии объясняют причины. Удалять мёртвый код и временные debug-вставки в своём diff; чужую работу не чистить заодно.

ViewModel не запускает работу при каждой recomposition, не проглатывает cancellation и не хранит медиа/секреты в SavedState. I/O не блокирует Main. Ошибки — явные состояния с возможностью retry, а не пустой «успех». Тексты в resources, визуальные значения в теме, lifecycle ресурсов явно определён. Общие рекомендации по state ownership и UDF сверены с [Android Developers](https://developer.android.com/topic/architecture/recommendations); подробные правила проекта находятся в соответствующих skills.

Для новой возможности сначала искать существующий код, затем официальную платформенную библиотеку, опубликованные пакеты и поддерживаемые upstream-проекты. Выбор проверяется на лицензию, совместимость, сопровождение, транзитивные зависимости и реальные тесты. Самостоятельная реализация требует причины; небольшая предметная функция не требует библиотеки. Решение о добавленной зависимости фиксировать компактно в `docs/dependencies.md`, когда первая такая зависимость действительно появится.
