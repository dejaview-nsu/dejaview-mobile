# Как поручать работу агентам

Задача приходит сообщением или ссылкой на локальную карточку Dev. **Redmine для мобильной части не используется.** Человеческое ревью желательно, особенно для auth, общих контрактов и зависимостей; его отсутствие не блокирует выполнение задачи. Самопроверка и автоматические проверки обязательны.

## Быстрый старт

Выдайте задачу вместе с `$dejaview-pipeline`. Если клиент не поддерживает вызов по имени, попросите прочитать `.agents/skills/dejaview-pipeline/SKILL.md`. Общие правила находятся в [AGENTS.md](../AGENTS.md). Все 13 skills написаны на английском; обсуждение и итог остаются на языке пользователя. Для Claude Code выполните `python scripts/sync_skills.py`; [CLAUDE.md](../CLAUDE.md) подключает общие правила. Канонические файлы — `.agents/skills`, локальные копии менять не нужно.

```text
Используй $dejaview-pipeline. Выполни D2-04 из docs/planning/dev-2.md.
Роль: Dev 2. Результат: два списка и единое состояние с карточкой фильма.
Область: feature/library и core/contracts/personal. Необходимую миграцию
потребителей выполни согласованно и объясни в итоговом diff.
Приёмка: пагинация, сортировка, независимые отметки, 204, ошибки,
отмена и поздние ответы покрыты автоматическими тестами.
Дизайн возьми из docs/design; сырые макеты остаются приватными.
Сначала ищи существующие решения, затем проверь подходящие библиотеки.
Доведи работу до реализации, проверок и небольшого готового к PR diff.
В итоге дай AC → тест → результат и оставшиеся зависимости.
```

## Что включать в промпт

| Поле | Содержание |
| --- | --- |
| Результат | Наблюдаемое поведение пользователя, не только имя класса |
| Контекст | Карточка Dev/UC, описание ошибки, существующий экран |
| Scope | Включённые и отложенные сценарии, владелец и модули |
| Приёмка | Успех и существенные альтернативы, которые должны работать |
| Дизайн/API | Каталог/nodeId и выбранный baseline; секреты только локально |
| Передача | Локальный diff или явно порученный commit/PR; merge отдельно |

Не требуется перечислять классы и библиотеки: агент исследует код. Для короткой задачи сам выводит требования из UC и сообщает предположения. Существенную неоднозначность уточняет, продолжая независимую работу. Новые требования можно прислать в тот же чат.

Пример бага: «При повторном поиске отображается ответ первого запроса. Воспроизведи регрессионным тестом, исправь, проверь отмену и поздний ответ». Пример UI: «Реализуй frame по nodeId из каталога, сохрани MVVM, выдели состояния и добавь Compose/screenshot проверки». Пример рефакторинга: «Сохрани поведение, сократи ответственность компонента, начни с текущих tests, не меняй API без необходимости».

## Пайплайн

1. Прочитать задачу, status/diff, UC и код; выделить AC-1…AC-N, scope и зависимости.
2. Выбрать подходящие skills. Для экрана прочитать Figma либо приватные JSON/PNG, проверить номер и состояния. Отсутствие PNG не скрывать под заявлением о визуальной приёмке.
3. Найти компоненты/библиотеки в repo, затем проверить платформенные решения, registry и upstream. Проверить лицензию, поддержку и совместимость; обосновать выбор или собственный код.
4. Спроектировать MVVM-состояния, domain/data границы, композицию экрана и таблицу тестов. Разбить большую работу на небольшие связные изменения.
5. Реализовать с тестами, выполнить проверки и исправить причины ошибок. Не обновлять snapshots/пороги ради зелёного CI.
6. Отдельным проходом проверить финальный diff: требования, архитектура, privacy и случайные файлы. Повторить нужные проверки после исправлений.
7. Передать выполненные критерии, фактические результаты и небольшой PR-diff. Невыполненный live/device/visual check пометить NOT RUN.

## Какие skills читать

| Задача | Skill |
| --- | --- |
| Общий цикл реализации/исправления | dejaview-pipeline |
| Kotlin/Compose, MVVM, SOLID | dejaview-code-style |
| Тесты, coverage, регрессия | dejaview-testing |
| Библиотеки и сложные общие возможности | dejaview-dependencies |
| Scaffold/Gradle/DI | dejaview-module |
| UC/экран/ViewModel | dejaview-feature |
| HTTP/DTO/backend | dejaview-api |
| Файлы, медиа, запись | dejaview-media |
| Session/login/CAPTCHA/OIDC | dejaview-auth |
| Figma/UI/экспорт | dejaview-design |
| Общие интерфейсы | dejaview-contract |
| Публичные материалы/данные | dejaview-privacy |
| Завершение и самопроверка | dejaview-pr |

Не читать все skills на каждую задачу. Для текстового поиска: pipeline → code-style/testing → feature/design/api → pr. Для документа — сокращённый pipeline и privacy/pr, без искусственных Android-тестов.

## Маленькие PR и чистота

Один PR — одно проверяемое поведение или подготовка, обычно 200–500 написанных строк. Generated/fixtures учитывать отдельно. Большой diff делить по смыслу, сохраняя собираемость. Отсутствие ревью не разрешает автоматический merge.

Стабильные решения обновлять в существующих docs, временные заметки/эксперименты/скриншоты держать в `.local`. Не создавать отчёты на каждый шаг, sample apps, копии планов и commented-out code. Build/cache игнорировать. Не чистить чужие изменения. Параллельные задачи используют отдельные ветки/worktrees и согласованное владение файлами; это не поручение самовольно запускать дополнительных агентов.

## Автоматическая проверка

```text
npm ci --prefix tools/design --ignore-scripts
python scripts/quality_gate.py
python scripts/sync_skills.py
```

Сейчас gate проверяет документы, privacy и инструменты. При появлении wrapper/Android-исходников автоматически потребует Android-настройку; пустая конфигурация даст ошибку. [Архитектура](engineering.md) и [тестовая политика](testing.md) определяют действия D1–D3. Android scaffold пока отсутствует, поэтому нынешняя проверка не подтверждает качество будущего приложения.

Skills не являются изоляцией файловой системы и не гарантируют безошибочную работу модели. Нужно различать PASS / FAIL / NOT RUN. Live CAPTCHA, физический микрофон и первичная оценка screenshot baseline иногда требуют целевой ручной проверки; агент должен назвать конкретный оставшийся сценарий, а не просить вручную перепроверить всё приложение.
