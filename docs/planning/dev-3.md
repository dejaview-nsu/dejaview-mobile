# План Dev 3 для DejaView Android

Сверка источников: [реализация backend](backend-evidence.md), [номера экранов Figma и PDF](../design/screen-map.md). Этапы обозначают объём Android, а не отсутствие серверного кода.

Ваша зона — безопасная работа с выбранными файлами, видео, локальная история и минимальный профиль. У вас нет задачи сделать весь редактор видео и полный профиль за две недели: триммер, Share и расширенный профиль выделены во второй этап.

Прочитайте [границы MVP](README.md), [контракты](contracts.md) и [матрицу требований](coverage.md). План: **48 ч задач + 12 ч D9–D10 = 60 ч**. D3 — ключ владельца, не календарный день.

## D3-01 Контракты и карта дизайна

**Файлы:** `core/contracts/media`, `core/contracts/history`, документация дизайна. **Потребители:** Dev 2/4 используют MediaStore, Dev 1 — HistoryRepository. Согласовать PreparedMedia, ID вместо raw path, семантику release и историю completion. Отдать stub и Fake в D1.

Собрать тестовые материалы с известными MIME, размером и длительностью: валидный/повреждённый файл, нулевая длина, лимит и превышение, inaccessible URI. Использовать материалы, которые команда вправе хранить; тяжёлые 50-МБ fixtures генерировать локально либо хранить вне git с инструкцией получения. Для реального распознавания нужны отдельные контрольные фрагменты из индексированного ML-каталога — запросить у ML команды.

Использовать готовые [каталог и токены](../design/README.md): извлечены 88 frames, 66 нумерованных экранов, 34 variables и 13 text styles. Завершить точные PNG/SVG через локальный экспортёр и сверить экраны своей роли. Figma выдала семь ссылок на PNG, но скачивание вернуло пустые ответы; валидных PNG пока нет, полный визуальный прогон не выполнен. Номера PDF местами расходятся с Figma — использовать screen-map.md, не выбирать frame только по номеру.

**Приёмка:** Dev 2/4 способны протестировать importer через Fake без готового видео; Dev 1 может записать/прочитать history Fake. Есть список экран → владелец → экспорт/нет экспорта. Контракты не импортируют Android Uri.

## D3-02 Импорт и временные файлы

**Модуль:** `core/media`; Android adapter вокруг content resolver. Принимать результат picker, копировать поток в private temp, определять метаданные, проверять ограничения, возвращать PreparedMedia. Размер провайдера может быть неизвестен или неверен — лимит проверяется при чтении. Нет преобразования URI в «настоящий путь» через устаревшие поля медиатеки.

Согласовать с Dev 2 способ открыть поток из data-слоя для multipart. Общая валидация формата/размера живёт здесь; каждая модальность передаёт policy, а не копирует три разных валидатора. Длительность проверяется в миллисекундах; не обрезать до целых секунд так, чтобы 30,9 с считались 30 с.

Контролировать закрытие потоков и release. Файл сохраняется для ручного retry после сетевой ошибки; удаляется при успехе, отмене или замене. Startup cleanup удаляет бесхозные файлы, не затрагивая активный draft. Оригинальные пользовательские файлы никогда не удаляются. Неудачное копирование/нехватка места не оставляют валидный ID с частичным содержимым.

**Приёмка:** null name/size/MIME, content URI внешнего provider, revoked permission, cancel во время копирования, недостаток места, повторный release, 50-МБ поток без чтения целиком в память. Тест metadata/валидации плюс instrumentation/manual smoke content resolver на устройстве. **Выход:** реальный MediaStore к D2–D3, пример использования Dev 2/4 и компактные fixtures.

## D3-03 Поиск по видео

**UC-08 частично, FR-06/04. Экраны:** 2.1, 2.5 без триммера, 2.8, 3.1, 3.3, 3.4, 3.5а. **API:** `POST /search/video`, multipart `file`. **Модуль:** `search-video`.

Сделать выбор одного готового MP4/MOV/WEBM фрагмента, импорт, превью, отправку и отмену. Ограничения — до 50 МиБ, до 30 000 мс. Ролик длиннее лимита в первой поставке получает сообщение с просьбой выбрать готовый короткий фрагмент; не показывать неработающую обрезку. Это исключение основного шага UC-08 явно отражено в матрице.

Media3 player освобождается при уходе; upload прогресс заканчивается переходом в Processing, а не обещанием найденного фильма. Реализовать Fake и API adapter, nullable mapper, события результата для оболочки. На смену режима/назад отменять собственную работу по согласованному lifecycle.

**Приёмка:** валидный клип распознаётся на стенде; 30 с включительно, 30 с +1 мс отклоняется; превышение размера, неподдерживаемый кодек, повреждение; 0/1 результат; отмена upload и игнорирование позднего ответа; retry после offline; 401 и 503. Проверить минимум на одном физическом устройстве, не обещать декодирование любого кодека лишь по расширению MOV/WEBM.

## D3-04 Локальная история

**UC-15 частично, FR-11. Экран:** 5.4 по Figma (5.9 — изменение имени). **Модули:** `core/storage`, `feature/history`. Серверного API истории в первой версии нет; FR-15 не реализуется.

Room entity: requestId unique, session namespace, mode, createdAt, text либо безопасные метаданные выбранного файла, result status, количество и информация о результате для перехода. Согласовать достаточный набор полей с Dev 1. Оригинальное медиа не хранить; отсутствие миниатюры даёт заглушку. Продумать миграцию/версию схемы; destructive migration не использовать как универсальное решение.

Оболочка Dev 1 — единственный writer. Обеспечить дедупликацию повторного completion, запись только success/empty. UI показывает свежие сверху, открывает фильм, подставляет старый текст в поиск, очищает историю. Повтор медиа предлагает выбрать файл заново. Пустая история и ошибка чтения различаются. У гостя история только в памяти; у авторизованного пользователя привязана к namespace входа.

**Приёмка:** перезапуск с действующей сессией сохраняет записи; logout/expire очищает namespace; вход другим аккаунтом не показывает прежние записи; два completion одного requestId дают одну строку; clear виден в UI сразу; ошибка записи истории не ломает найденный фильм. Тест DAO на устройстве/эмуляторе и тест ViewModel с Fake. Без стабильного server user ID не обещать историю между разными входами.

## D3-05 Минимальный профиль

**UC-15 и UC-16 частично. Экраны:** 5.3, 5.5 в урезанном составе; переход к истории 5.4. **Модуль:** `profile`. Источник данных — SessionReader Dev 4, а не выдуманный `/users/me`.

Показать username и доступный avatar URL/заглушку, пункты «Мои фильмы», «История поиска», «Выйти». Гостю — действие входа. Logout делегировать SessionController; профиль не создаёт собственный AuthApi. Статистика, редактирование имени, аватар, пароль, подписка и удаление профиля в первой поставке скрыты.

**Приёмка:** изменения сессии сразу отражаются в UI; вход из профиля возвращает туда; после logout back не открывает персональные данные; список и история открываются typed routes; сетевой сбой logout отображается без сохранения локальной cookie. Тест состояния и ручная проверка back stack.

## D3-06 Устройства и очистка ресурсов

На D8 проверить video/image/audio importer вместе с владельцами. Пройти поворот, уход в фон, пересоздание Activity, удалённый исходный файл, новый файл вместо старого, отказ permission и отмену. Сопоставить количество временных файлов до/после поиска; не должно быть утечки после успеха/отмены. Проверить, что player/recorder не продолжают работу после ухода с экрана (recorder исправляет Dev 4).

**Выход:** журнал проверенных устройств/API уровней и дефекты с воспроизведением; CI/инструментальный запуск по договорённости Dev 2. **Приёмка:** можно провести несколько последовательных поисков без зависшего player/роста временного каталога; нет показа персональной истории после смены пользователя.

## Передачи и второй этап

D1 — Media/History contracts и Fake; D2 — importer; D5–D6 — Room/history UI. В D1 запросить у Dev 4 session namespace, у Dev 1 — completion. Не хранить username как постоянный идентификатор владельца данных.

D9–D10, 12 ч: регрессия устройства/файлов/истории и исправления. Затем P2-07/08/09: триммер Media3, Share с извлечением кадра/звука и полный профиль. Триммер должен проверять **результат** экспорта; remux не превращает произвольный codec в поддержанный M4A автоматически.

Первая задача агенту: «Выполни кодовую часть D3-01: core/contracts/media и history, Fake и fixtures. Контракты должны быть без Android-типов, с явным release и unique requestId. Экспорт дизайна — отдельный результат, не заменяй его выдуманными tokens».
