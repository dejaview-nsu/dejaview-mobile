## D4-01 Сессия и защищённое хранение

**Файлы:** `core/contracts/session`, `core/security`. Отдать SessionReader/Controller, CookieStore и Fake в D1. Реализация хранилища использует ключ Android Keystore и зашифрованные данные на диске; DataStore сам по себе шифрования не даёт.

Сохранять cookie `dv_session` с атрибутами, сроком и scope. Не хранить пароль. Для восстановления состояния использовать `GET /auth/session`; response содержит username/avatar/has_password и expires_at, но **не user_id**. Согласовать session namespace истории с Dev 3. Для MVP новый login создаёт новый namespace, logout/expire очищают его.

Отдельно согласовать с Dev 2 порядок `Set-Cookie → persistence → SessionState`. Обеспечить, чтобы поздний ответ старого запроса после logout не восстановил cookie. При повреждении local storage/key — очистить локальную сессию и предложить войти заново, без crash. Исключить auth данные из логов и незашифрованного backup.

**Приёмка:** guest/initializing/auth/expired; перезапуск до expiry; expiry по времени и серверный 401; cookie не отправляется стороннему host; очистка после logout; одновременные 401 не создают несколько login экранов. Unit-тест state machine + устройство для реального Keystore/storage. Не считать Fake подтверждением работы шифрования.

## D4-02 Вход существующим аккаунтом

**UC-04 частично, FR-03. Экраны:** 1.3, 1.3а, 2.1б. **API:** `POST /auth/login`, `GET /auth/session`. **Модуль:** `auth`.

Форма login/email + password, видимость пароля, loading, полевые/общие ошибки. Проверять login и непустой пароль по выбранному контракту, не применять правила регистрации к уже существующему паролю. Кнопки регистрации/OIDC/reset отсутствуют в MVP, а подтверждённые аккаунты готовятся до тестирования.

Получить тестовый аккаунт и выполнить login/session smoke на стенде в D2. Проверить Set-Cookie, повторный session request и корректное expires_at, не ограничиваться 200 body. Обработка неподтверждённого email не должна давать успешный вход; в MVP показать необходимость подтверждения вне приложения, resend войдёт в P2-01. `AUTH_ACCOUNT_BLOCKED` и некорректные данные имеют разные тексты, без разглашения внутренних ошибок сервера.

**Fake:** success, invalid credentials, unconfirmed, blocked, captcha required, locked, offline, 500. **Приёмка:** успешный вход создаёт сессию; неуспех не оставляет cookie authenticated; повтор submit блокирован; секреты не сохраняются в navigation/SavedState/логах. UI тест входа с Fake и отдельный real smoke.

## D4-03 Возврат и выход

**UC-04 шаг 5; UC-16 только logout. Экран:** 5.5, auth prompt. **API:** `POST /auth/logout`. Вход возвращает через callback/route Dev 1; профиль Dev 3 вызывает ваш SessionController.

Проверить expected pendingActionId, success и cancel. Списки/рейтинг после login выполняют сохранённое желаемое действие; media возвращается к draft с кнопкой подтверждения. Повторная эмиссия session state не выполняет действие второй раз.

Logout очищает локальную сессию и персональное состояние даже при offline, а серверный сбой показывается. Новый login не может получить прежнюю историю/списки через незавершённый запрос старого поколения. При обычном 401 от фонового чтения публичная карточка остаётся доступной гостю; навигацию к login инициирует попытка защищённого действия, а не сетевой interceptor.

**Приёмка:** login/cancel из текста, изображения, карточки и профиля; истечение во время upload; logout во время запроса; back после выхода не раскрывает private экран. Потребительские проверки с Dev 1/3.

## D4-04 Поиск по аудио

**UC-09 без фоновой отправки; FR-07/04. Экраны:** 2.1, 2.6, 2.6а, 2.6б, 2.8, 3.1, 3.3, 3.4. **API:** `POST /search/audio`, multipart `file`. **Модуль:** `search-audio`.

Два входа: выбрать MP3/WAV/OGG/M4A документ либо записать микрофоном M4A/AAC. Ограничения — до 20 МиБ, до 10 000 мс. RECORD_AUDIO запрашивается при выборе записи, а отказ оставляет выбор файла доступным. Запись останавливается через 10 с; после остановки проверить фактическую длительность контейнера, а не только таймер UI. Если получился фрагмент выше лимита, не отправлять его молча.

Добавить прослушивание, удаление/перезапись, submit, byte progress и processing. Регистратор и player освобождаются при уходе, нет скрытой записи в фоне. Выбранный файл проходит MediaStore Dev 3, созданная запись регистрируется в том же жизненном цикле временных файлов. API не принимает raw PCM под MIME M4A; расширение не заменяет корректный контейнер.

**Приёмка:** файл и запись проходят real search; 0/1 результат; 10 с и превышение, 20 МиБ и превышение; permission denied/permanently denied; занятый микрофон/ошибка recorder; прерывание Activity; cancel upload и повтор; 401/413/415/422/503. Физическое устройство обязательно для записи и проверки playback, эмулятор не единственное доказательство. Историю записывает оболочка, а не аудиомодуль.

## D4-05 CAPTCHA и защитные ошибки

**UC-04 альтернативы б–г в включённой части. API:** login с `captcha_token`, ответ `AuthLoginError.captcha_required`, 429 и Retry-After. По PDF CAPTCHA выводится через страницу сервиса; URL и протокол возврата токена в OpenAPI не определены — это внешний блокер Q-03.

Запросить в D1/D2 готовую HTTPS-страницу и origin, процедуру выдачи токена, тестовый режим на стенде. До готовности делать UI/Fake, не снимать серверную проверку. При `captcha_required` запускать согласованный trusted flow, получать свежий token на попытку, отправлять с login. WebView, если выбран, ограничить доверенной страницей и минимальным bridge; не принимать токен из произвольного redirect/origin.

429 показывает срок повторной попытки по серверному Retry-After, а не локальному счётчику «три/пять попыток». CAPTCHA required/invalid, unconfirmed email и blocked account не являются SessionExpired. UI не содержит обещания автоматического разблокирования без серверного подтверждения.

**Приёмка:** серверный challenge реально появляется, верный token завершает login, неверный/просроченный даёт корректный повтор; закрытие страницы возвращает форму; 429 запрещает ранний submit и разрешает после срока; переход на посторонний origin не получает bridge. Если D6 flow не готов, обозначить блокер **реального MVP**, а не объявлять UC-04 полностью завершённым.

## D4-06 Сессионная и аудио регрессия

Проверить cold start с действующей/истёкшей/повреждённой cookie, сетевую ошибку restore, concurrent 401, logout во время запроса и смену аккаунта. Повторить запись/отмену/перезапись несколько раз, убедиться, что микрофон и временные файлы освобождены.

**Выход:** тестовые сценарии и реальные результаты к D8. **Приёмка:** у приложения нет Bearer token вместо dv_session, секретов в APK fixtures/логах, вечной авторизованной FakeSession в prod; серверный login/session и audio работают на одном выбранном стенде.

## Передачи и следующий этап

D1 — session Fake всем, CookieStore Dev 2, namespace Dev 3. D2 — живой login/session; D4 — возврат и logout; D6 — audio. Разбор UI `Set-Cookie` не дублируется в сетевом модуле; нужна одна согласованная последовательность состояния.

D9–D10, 12 ч: реальные сессии/CAPTCHA/аудио и устранение дефектов. После MVP — P2-01/02/03: регистрация/подтверждение, восстановление/смена пароля, OIDC PKCE. PendingUploadWorker передаётся в отдельный межмодульный пакет P2-11; добавлять его к вашей первой неделе нельзя.

Первая задача агенту: «Выполни D4-01 в core/contracts/session и core/security. Интерфейс CookieStore согласуй с contracts.md. Реализуй Fake и защищённое хранилище, учти поздний ответ после logout. Не реализуй OIDC, reset-password и Worker. Приложи проверки, отдельно укажи, что требует устройства».
