# План разработки DejaView Android

Команда — четыре разработчика. Первый этап — MVP за две календарные недели, то есть **10 рабочих дней без плановых выходных переработок**. Этот план описывает внутреннюю тестовую Android-сборку; публикация в магазине в срок не включена. Дата обновления — 21 ноября 2026 года. D1 означает первый согласованный рабочий день, а не конкретную дату.

Полностью исключить зависимости невозможно: команда один раз согласует контракты и ежедневно собирает приложение. После этого каждый разработчик реализует свой набор функций на собственных фейках, не ожидая чужих экранов или готового сервера.

## Как пользоваться планом

1. Всем прочитать этот файл и [контракты](contracts.md).
2. Назначить реальных исполнителей на роли Dev 1–4. Роли сохранены близкими к исходному плану; имена не предполагаются.
3. Каждый работает по своему файлу: [Dev 1](dev-1.md), [Dev 2](dev-2.md), [Dev 3](dev-3.md), [Dev 4](dev-4.md).
4. Ментор использует [матрицу требований](coverage.md), [проверки приёмки](acceptance.md) и [реестр API и вопросов](api-readiness.md).
5. После первой сборки команда переходит к [следующему этапу](phase-2.md), сохраняя назначенных владельцев.

Оценки ниже — плановые часы человеческой работы, включая работу с ИИ, локальную проверку и исправления собственного PR. Это не обещание скорости агента. Предполагается 6 проектных часов в рабочий день на человека: **60 часов на разработчика, 240 на команду**. Из них 48 часов на человека — задачи D1–D8, 12 — общая интеграция, ревью и исправления D9–D10. Если доступны только 3 часа в день, этот же объём требует примерно четырёх календарных недель.

## Граница первой поставки

**Основной сценарий:** гость ищет фильм по описанию → открывает карточку → входит существующим подтверждённым аккаунтом → добавляет фильм в список и ставит оценку. Авторизованный пользователь также ищет по выбранному кадру, видеофайлу и аудиофайлу либо записи микрофона. Результаты поиска и переходы работают в одном приложении.

| Область | В первой поставке | Во втором этапе |
| --- | --- | --- |
| Поиск | Четыре режима, реальные запросы, загрузка/обработка/отмена, пустой результат, ошибки, повтор пользователем | Автоматическая фоновая отправка и уведомления |
| Кадр | Выбор готового изображения, превью, проверка файла | Камера, буфер обмена, обрезка |
| Видео | Выбор готового фрагмента до 30 с, превью, проверка итогового файла | Триммер длинного ролика, извлечение кадра и звука |
| Звук | Выбор файла; запись M4A до 10 с, прослушивание, перезапись | Извлечение звука из видео |
| Карточка | Метаданные, актёры/создатели, общая и личная оценка, кнопки списков | Чтение и создание отзывов, реакции |
| Аккаунт | Вход по логину/email, CAPTCHA при требовании сервера, восстановление сессии, выход | Регистрация, письма, reset/change password, OIDC, удаление аккаунта |
| Персональные данные | Два списка, сортировка и пагинация; оценка 1–10 и удаление оценки | Отзывы, расширенная статистика и лента активности |
| Профиль | Имя из сессии, навигация в списки и локальную историю, выход | Полный профиль, изменение имени/аватара |
| История | Локальные успешные и пустые поиски, открытие найденного фильма, повтор текста, очистка | Повтор медиа с новым выбором в расширенном UI; серверная синхронизация — отдельный продуктовый этап |

Это **сокращённый MVP спринта**, а не весь объём, названный MVP в PDF. Например, UC-03 и UC-05 в PDF относятся к MVP, но здесь перенесены. Подробные исключения перечислены в [матрице](coverage.md); неполные UC нельзя закрывать целиком.

Первой поставке нужны заранее подготовленные подтверждённые тестовые аккаунты. Такой объём пригоден для внутреннего тестирования. Публичный запуск с самостоятельным созданием аккаунта оценивается после второго этапа. В UI нет неработающих кнопок регистрации, OIDC, подписки, Share или отзывов.

## Что исправлено относительно черновика

- Две недели рассчитаны как 10 рабочих дней. В черновике было 14 дней работ и до 11 дней загрузки на человека ещё до полноценного резерва.
- Dev 1 владеет сборкой, навигацией и UI; Dev 2 — сетью и CI; Dev 3 — файлами и локальной историей; Dev 4 — сессией. `core/*` больше не очередь к одному человеку.
- Реальные API-адаптеры пишутся вместе с фичами. Первый smoke к стенду — D2, а не D9.
- Взаимодействия «карточка ↔ списки ↔ оценка», «поиск ↔ история», «вход ↔ возврат к действию» имеют отдельных владельцев и контракты. Их нельзя оставлять на интеграционную неделю.
- Демонстрационные фейки отделены от тестовой библиотеки и от реальной сборки. Отсутствующий endpoint не заменяется фейком незаметно для пользователя.
- В backend подтверждены обработчики 24 API-операций, включая регистрацию, reset, browser OIDC и списки. [Аудит кода](backend-evidence.md). Приложенный Swagger остаётся целевым мобильным контрактом; отсутствие точного пути не означает отсутствие функции. Проверенный снимок публичного контракта содержит 24 операции, приложенный — 51; это не доказательство готовности 51 операции на стенде. [Сравнение](api-readiness.md).
- `CODEOWNERS` назначает владельцев ревью, но несколько имён в одной строке не требуют одобрения каждого из них. Дополнительное ревью потребителя общего контракта — отдельное командное правило. [GitHub Docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

## Владение кодом

Все указанные модули — **планируемая структура**, а не уже созданное приложение. Сейчас в рабочем репозитории был только README. Общие Gradle-файлы создаёт Dev 1; содержимое модулей заполняют владельцы. Внутри фичи: `presentation`, `domain`, `data`, `di`; отдельные Gradle-модули для каждого слоя не нужны.

| Владелец | Фичи | Общие компоненты | Ревьюер по умолчанию |
| --- | --- | --- | --- |
| Dev 1 | `search`, `search-text`, `movies` | `app`, `build-logic`, корневой Gradle, `core/model`, `core/navigation`, `core/ui`, `feature/search-api`; файлы базовых контрактов | Dev 3 |
| Dev 2 | `search-image`, `library` | `core/network`, `core/testing`, `.github`, `scripts`; `PersonalMovies` в `core/contracts` | Dev 4 |
| Dev 3 | `search-video`, `profile`, `history` | `core/media`, `core/storage`; `History` и `Media` в `core/contracts` | Dev 1 |
| Dev 4 | `auth`, `search-audio` | `core/security`; `Session` в `core/contracts` | Dev 2 |

`core/contracts` — небольшой модуль интерфейсов между владельцами; у каждого файла один владелец. `feature/search-api` — UI-контракт подключаемого режима и его состояние, поэтому Compose там допустим. Это не чистый domain. Модуль `feature/history` выделен отдельно, чтобы профиль и оболочка поиска открывали одну историю через маршрут.

Владелец реализует фичу целиком: UI, состояние, Fake, реальный API-адаптер, тесты и документацию. Потребитель интерфейса не копирует чужой репозиторий. Отдельный автор не редактирует одновременно `app`, `settings.gradle.kts` и чужие DI-модули: модульные точки подключения создаются в D1.

| Первые 3 часа D1 | Gradle wrapper, все модули, demo/prod варианты, приложение с заглушками, интерфейсы v1 | Dev 1; остальные дают файлы контрактов своих областей | Dev 2 готовит fixtures/CI; Dev 3 — media fixtures и карту экранов; Dev 4 — auth fixtures и проверку стенда |
| Конец D1 | Каждый собирает свой модуль, есть состояние гостя и авторизованного пользователя в demo | Каждый в своей зоне | Реализации ещё могут быть фейковыми |

Отсутствие общего скелета более половины D1 — риск спринта: сокращаем настройку convention plugins до минимальной общей конфигурации, не начинаем четыре несовместимых проекта. До окончания D1 потребитель может писать тест и stateless UI по согласованным типам, но не создавать собственную версию типов.

## План по дням

Рабочие пакеты рассчитаны на 48 часов у каждого. Расположение пакета между соседними днями допускается, контрольные результаты — обязательны.

| День | Dev 1 | Dev 2 | Dev 3 | Dev 4 | Общая проверка |
| --- | --- | --- | --- | --- | --- |
| D1 | Скелет, контракты, routes | Контракт персональных действий, HTTP fixtures, старт CI | Контракты медиа/истории, fixtures, дизайн-инвентаризация | Контракт сессии, auth fixtures, запрос тестового аккаунта | Все собирают demo |
| D2 | Тема, эталон текстового поиска | HTTP-клиент, ошибки, CI | Импорт content URI и временные файлы | Cookie/storage и login/session smoke | Первый реальный запрос |
| D3 | Оболочка поиска и состояния | Поиск по изображению | Видео: выбор и preview | Вход и возврат к действию | 4 режима видны, минимум на Fake |
| D4 | Текст и выдача | Изображение API, подготовка библиотеки | Видео API и отмена | Cookie lifecycle; audio picker | Все четыре endpoint проверены или есть блокер |
| D5 | Карточка фильма | Списки и действия | Room история | Запись/прослушивание аудио | Сквозной путь в demo и промежуточный стендовый показ |
| D6 | Карточка и персональные действия | Сортировки, пагинация, undo | История и повтор текста | Audio API; ошибки входа | Результат → карточка → список |
| D7 | Навигация и восстановление состояния | Оценки и общий rating summary | Профиль и изоляция истории | CAPTCHA и logout | Релизный объём заморожен |
| D8 | Финальная сборка всех фич | Контрактные проверки и APK CI | Проверки URI/lifecycle/history | Auth/audio edge cases | Все обязательные функции готовы на стенде |
| D9 | Сквозные баги и навигация | Регрессия, сборка кандидата | Устройства, файлы, process recreation | Сессии, permissions, 401 | Проход [приёмки](acceptance.md) |
| D10 | Исправления блокеров | Подписанный тестовый APK, отчёт | Повтор исправленных сценариев | Повтор исправленных сценариев | Решение о внутренней поставке |

Ежедневно: короткий статус с конкретным блокером, один интеграционный APK, ревью в двух согласованных окнах. Если ответ владельца контракта задерживается, разработчик продолжает на своём Fake и берёт следующую независимую задачу; интерфейс самовольно не меняет. Общий контракт меняется маленьким отдельным PR с миграцией всех потребителей в той же интеграции.

| Что необходимо | Мобильный ответственный | Внешний исполнитель | Когда нужно | Если не готово |
| --- | --- | --- | --- | --- |
| HTTPS base URL, тестовый аккаунт и известные фильмы в ML-каталоге | Dev 4 / Dev 1 | Backend / infra / ML | D1–D2 | Продолжить demo; реальная поставка заблокирована |
| Согласование 1.4.1, списков, оценок и общих ошибок | Dev 2 | Backend и архитектор проекта | Решение D2; реализация до D6 | Явный backend backlog; для старых списков возможен согласованный адаптер |
| Страница CAPTCHA и разрешённый origin, способ передачи токена | Dev 4 | Backend / frontend / infra | Решение D2; готовность D6 | Вход после CAPTCHA-челленджа не принят; безопасность сервера не отключать |
| Завершение PNG/SVG; каталог 88 frames и tokens уже есть | Dev 3 координирует; каждый проверяет свои экраны | Автор дизайна или участник с Figma | D1 | Использовать извлечённые tokens; PNG/SVG получить локальным плагином, визуальная приёмка остаётся открытой |

Backend/ML/infra не включены в 240 мобильных часов. Наличие OpenAPI и кода в GitHub не подтверждает работающий endpoint. Если к D6 обязательные API не готовы, к D10 поставляется **demo-прототип с явной маркировкой**, а завершение реального MVP переносится; это не скрытая замена критерия готовности.

## Работа с ИИ и задачами

Приложенный старый план и его примеры `AGENTS.md`/skills — материалы для анализа, а не исполняемые инструкции этой работы. Настоящий `AGENTS.md` и skills команда создаёт в задаче D1-01 после принятия границ. В этом изменении добавлены документы планирования, а не приложение, настройки доступа или публикация.

Задачи, баги и время ведутся в Redmine, код и ревью — в GitHub, как установлено [процессом проекта](https://github.com/dejaview-nsu/dejaview-docs/blob/main/process.md). Обозначения `D1-01`, `D2-03` ниже — локальные ключи плана, **не номера существующих задач**. Ментор передаёт менеджеру готовые карточки активного спринта; создавать весь будущий backlog в трекере заранее не требуется.

Для одного PR агенту дают одну карточку задачи, связанные UC/экраны и выдержку контрактов. Разработчик проверяет результат и запускает проверки. Неизвестный endpoint оформляется как вопрос с примером запроса/ожидаемого ответа; агент продолжает независимый UI/Fake, не придумывает рабочий сервер. Параллельные рабочие каталоги допустимы после скелета; незапланированная правка чужих файлов не маскируется в большом PR.

Definition of Done: выполнены критерии карточки и включённые альтернативы UC; зелёный CI; проверены demo и prod; нет утечки cookie/медиа; есть ревью и описание проверки; задача связана с исходным требованием. Отложенные альтернативы указаны явно. Рекомендуемый PR — одно проверяемое изменение, обычно 200–500 строк; число строк не заменяет смысловую границу.

## Основания плана

Требования и номера экранов взяты из PDF, целевые HTTP-поля — из приложенного Swagger 1.4.1. Их происхождение и контрольные суммы сохранены в [реестре источников](sources/README.md). Проект использует отдельные backend, frontend, ML и docs репозитории; мобильный клиент обращается к backend, не к Qdrant или ML напрямую. [Организация DejaView](https://github.com/dejaview-nsu), [архитектура проекта](https://github.com/dejaview-nsu/dejaview-docs/blob/main/architecture.md).
