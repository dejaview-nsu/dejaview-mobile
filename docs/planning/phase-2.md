# Разработка DejaView после первого MVP

Сверка источников: [реализация backend](backend-evidence.md), [номера экранов Figma и PDF](../design/screen-map.md). Этапы обозначают объём Android, а не отсутствие серверного кода.

Этап 2 завершает возможности, помеченные как MVP в исходном PDF, но исключённые из двухнедельного спринта. Его начало — после принятого API baseline и стабильной первой сборки. Оценки ниже — диапазоны человеческих часов без внешней разработки backend/infra. Это отдельный план, не скрытая нагрузка первых двух недель.

Рабочий ориентир — **ещё 3–4 календарные недели** при прежних 6 проектных часах в день и готовых внешних зависимостях. После первых двух дней технических проб триммера и OIDC диапазоны нужно уточнить. На интеграцию добавить 20% к задачам, не заполнять весь календарь функциями. Узкие места — медиа у Dev 3 и auth у Dev 4; свободное время Dev 1 направляется на общую интеграцию и взаимную проверку.

## P2-01 Регистрация и подтверждение

Dev 4 реализует UC-03, экраны 1.4/1.5/1.5а, API register/confirm-email/resend-confirmation. Поля username/email/birth_year/password сверяются со схемами; URL условий и поведение согласия берутся из решения Q-10. Ссылка подтверждения открывается по `/confirm-email`, проверяется в приложении, session берётся из native HTTP ответа.

Приёмка: занятый username/email, невалидные поля, повтор письма через серверный срок, истёкшая ссылка, успешное подтверждение и вход, открытие письма на другом устройстве/в браузере. Domain/assetlinks и реальный доставленный email обязательны для интеграции. Существующий черновик действия после входа не теряется.

## P2-02 Восстановление и смена пароля

Dev 4: экраны 1.7/1.7а/1.8/1.5а/5.6; POST password-reset/request/check/complete, PUT `/users/me/password`. Профиль Dev 3 лишь открывает route. Ссылка reset одноразовая, срок 1 ч; после reset проверить прекращение прежних сессий и созданную по контракту новую сессию. При change-password учитывать has_password=false.

Приёмка: одинаковое сообщение request для существующего и отсутствующего аккаунта, неправильный/повторно использованный token, password rules/confirmation, browser fallback, неверный текущий пароль, сохранение текущей сессии и завершение других при profile password change. Password/token не сохраняются в логи и обычное состояние навигации.

## P2-03 Внешние провайдеры

Dev 4: экраны 1.3/1.6/1.6а; start → backend callback → App Link `/app/oidc` → exchange → session либо pending/complete/login. Android создаёт state/code_verifier и S256 challenge; backend обменивает код провайдера. Cookie браузера не является сессией OkHttp. Нужен реальный POST `/auth/oidc/exchange`.

Приёмка каждого VK/Яндекс/Google: уже связанный аккаунт; новый аккаунт с дооформлением; совпавший email с подтверждением пароля; cancel/error; неверные state/verifier, истёкший/повторный одноразовый код; pending cookie `dv_oidc` с правильным path/expiry. После ошибки одноразового обмена процесс запускается заново, а не бесконечно повторяет использованный code. Секрет провайдера никогда не хранится в APK.

## P2-04 Отзывы

Dev 1 владеет чтением GET `/movies/{movie_id}/reviews`, экраном 4.5 и сортировками best/worst/newest/oldest, страницами по 10. Dev 2 владеет редактором 4.4 по Figma (4.3 — отдельная оценка), GET/PATCH/DELETE `/reviews/{review_id}` и POST `/movies/{movie_id}/reviews`. Между ними — route editor(movieId, reviewId?) и событие результата, не доступ к ViewModel друг друга.

Приёмка: обязательный verdict, title ≤150, text 300–10 000, один отзыв на фильм, create/edit/delete, 403 чужого отзыва, duplicate conflict, sort/page reset, автор после удаления аккаунта, пустой список. Закрытие редактора обновляет отзывы карточки и профиль. Оценка фильма остаётся отдельной операцией.

## P2-05 Реакции

Dev 2 реализует PUT/DELETE `/reviews/{review_id}/reaction` и общий review-state adapter; Dev 1 подключает кнопки к своему списку. Приёмка: поставить вверх/вниз, сменить, снять повторным нажатием; запрет собственного отзыва и серверный 403; корректный rollback/сохранение предыдущего состояния при сети; отсутствие двойного счётчика при повторе.

## P2-06 Камера и обрезка кадра

Dev 2 добавляет camera capture, permission/settings fallback, clipboard import и crop в UC-07, экраны 2.3/2.3а/2.4. Готовый результат проходит тот же MediaStore и лимит, что файл из галереи. Crop-компонент пригоден для аватара, но uploader аватара отдельный.

Приёмка: отказ камеры, поворот/ориентация EXIF, большой снимок без OOM, отмена crop, замена исходника, недоступный clipboard URI, проверка реального размера результата. Наличие CameraX не заменяет пользовательский сценарий permission.

## P2-07 Триммер видео

Dev 3 добавляет выбор диапазона ≤30 с и экспорт через Media3 Transformer. Технология поддерживает обрезку/преобразования; доступность codec проверяется на целевых устройствах. [Android Media3 Transformer](https://developer.android.com/media/media3/transformer).

Приёмка: исходник длиннее 30 с, перемещение диапазона, отмена экспорта, финальная длительность и размер ≤50 МиБ, недостаток места, неподдерживаемый codec, cleanup. Исходный большой файл не отклонять только по лимиту **выходного** фрагмента, но задать отдельный согласованный технический предел импорта/обработки. Не выдавать огромный исходник за готовый PreparedMedia поиска до trim.

## P2-08 Системное Поделиться

Dev 3 создаёт отдельную share entrypoint и intent filters, согласованный небольшой wiring PR у Dev 1. ACTION_SEND/ACTION_SEND_MULTIPLE принимают image/video content URI; multiple открывает выбор одного. Для видео: поиск по самому клипу, выбранному кадру или звуку. URL на ролик из соцсети не равен переданному видеофайлу: unsupported text/link обрабатывается явно, скачивание произвольных соцсетей не входит в требования.

Frame extraction отдаёт PreparedMedia Dev 2; audio extraction — Dev 4. Кадр выбирается по моменту, звук ограничивается 10 с. Remux подходит только для совместимого содержимого, иначе нужен согласованный transcode либо сообщение об ограничении.

Приёмка: cold/warm start, multiple, revoked grants, login-return с сохранённым импортом, intent повторно доставлен, cancel, frame/audio/video результат. Передачу между фичами организует app/coordinator через контракты, а не прямые импорты.

## P2-09 Полный профиль

Dev 3 реализует `/users/me` GET/PATCH, statistics/actions/ratings/reviews GET, экраны 5.3/5.3а/5.3б/5.4/5.5/5.9. Пагинация и сортировки строго по выбранной схеме. Username editable, email/birth_year/created_at read-only; linked providers отображаются без функции отвязки.

Приёмка: занятое имя, empty lists, переходы к фильму/отзыву, обновление после mutation Dev 2, no password account, logout isolation. Stable user ID согласуется с backend до миграции истории; переименование username не создаёт нового владельца истории. Повтор media требует выбрать исходник, если файла уже нет. Серверная синхронизация истории остаётся этапом 3.

## P2-10 Аватар и удаление

Dev 2 использует crop/importer для UC-20: JPG/PNG до 5 МБ, min 200×200, квадрат, JPEG 1024×1024, PUT/DELETE `/users/me/avatar`. Dev 3 подключает entrypoint 5.8 и обновление профиля. Приёмка: недостаточное разрешение, размер/формат, cancel, upload fail, удаление и обновление avatar в session/header.

Dev 4 реализует опасное account action UC-18: экран/диалог 5.7, предупреждение, ввод username и DELETE `/users/me`. Username подтверждается в UI; не добавлять выдуманное поле request body. После 204 очищаются session, personal cache, локальная история и pending media/jobs. Сервер оставляет оценки/отзывы анонимными — это проверяется на стенде отдельно. Cancel и server failure не должны сообщать об удалённом аккаунте.

## P2-11 Отправка после восстановления сети

Dev 1 владеет отдельным `feature/pending-search` и WorkManager orchestration; Dev 3 — durable file/Room job; Dev 4 — привязкой к stable account и возобновлением после login. Модальности передают задание через контракт SearchSubmission, а не создают три Worker. Потребуется versioned migration контрактов: выполнить её одним интеграционным пакетом после фиксации схемы.

Job содержит уникальный requestId, owner account ID, mode, media reference, состояние и TTL. Файл pending живёт дольше обычного cache draft. WorkManager ждёт сеть; 401 переводит в WaitingForAuth, а вход **другого** пользователя не отправляет старый файл. Настоящий стабильный user ID обязателен до выпуска этого поведения.

Retry: validation/403 не повторять автоматически; 429 учитывать серверный срок; transient errors — ограниченные backoff/attempts. При обрыве после отправки сервер мог уже обработать POST: без серверной идемпотентности нельзя обещать exactly-once. Согласовать допустимость повторов/ключ с backend до реализации. Локальная история дедуплицирует requestId независимо от количества попыток.

Приёмка: сеть пропала/вернулась, процесс убит, перезагрузка, expiry/login того же и другого аккаунта, cancel job, deleted media, уведомление и отказ permission уведомлений, переход к результату, logout/delete cleanup, лимит retries и TTL. При отказе уведомлений результат всё равно доступен в истории.

Этим работам нельзя назначить достоверный двухнедельный срок по текущим материалам: для четырёх последних функций нет соответствующих операций в приложенном Swagger. Сначала продуктовые/API решения, затем отдельные карточки. Цены/провайдеров/магазинные правила из старого документа не считать автоматически актуальными на момент реализации.
