# План Dev 1 для DejaView Android

Сверка источников: [реализация backend](backend-evidence.md), [номера экранов Figma и PDF](../design/screen-map.md). Этапы обозначают объём Android, а не отсутствие серверного кода.

Ваша зона — сборка приложения, навигация, общий UI, оболочка поиска, текстовый режим и карточка фильма. Результат роли: пользователь проходит от запуска приложения до фильма, а независимые реализации остальных разработчиков подключаются без переделки навигации.

Сначала прочитайте [границы MVP](README.md) и [контракты](contracts.md). Префикс D1 в ключе задачи означает Dev 1, а не день спринта. План: **48 ч задач + 12 ч D9–D10 = 60 ч**. Фичи D2/3/4 нельзя реализовывать внутри `app` ради ускорения интеграции.

## D1-01 Скелет и интерфейсы

**Вход:** исходный README, [список модулей](README.md), файлы контрактов владельцев Dev 2–4. **Файлы:** `app`, `build-logic`, `gradle/libs.versions.toml`, корневые Gradle-файлы, `core/model`, `core/navigation`, базовая часть `core/contracts`, `feature/search-api`, документация агента.

Создать Kotlin/Compose приложение, Gradle wrapper и пустые модули всей первой поставки. Зафиксировать совместимые JDK, AGP, Kotlin, KSP, Compose, Hilt и Navigation в version catalog. Создать demo/prod flavor, начальный `AppNavHost` с заглушками и заранее подключить feature DI. Согласовать minSdk с тестовыми устройствами; рабочее предложение — API 26, решение записать. Compile/target SDK выбрать из реально установленного совместимого toolchain; не считать это решением о требованиях публикации в магазине.

Создать routes: Search(mode, draftId?), Results(requestId), Movie(movieId), Login(pendingActionId?), Library(list), Profile, History. Принимать контракты других владельцев, не переписывать их реализации. Минимальные правила агенту: разрешённые пути, команда сборки, ссылка на UC, запрет выдумывать API, порядок работы с изменением контракта. Установка набора skills не является блокером сборки.

**Выход:** первый PR со скелетом за первые 3 часа; вторым небольшим PR — правила и подтверждённые зависимости. **Приёмка:** чистый checkout собирает demoDebug и prodDebug, экран запуска открывается, каждый владелец компилирует свой модуль; в prod нет случайных demo binding. Все варианты DI без дублирующих providers.

**Что можно делать без коллег:** сборка, маршруты и базовые модели. Если контракт ещё обсуждается — оставить одну явно согласованную stub-реализацию, не внедрять параллельную модель.

## D1-02 Тема и компоненты

**Требования:** FR-04 и общий UI всех экранов. **Владеете:** `core/ui`; остальные используют компоненты и не правят тему. Нужны токены/экспорты от задачи D3-01; пока доступны только PDF IDs и обзорная миниатюра FIG, точные значения не выдумывать.

Создать тему, типографику, отступы, кнопку primary, поле ввода, переключатель режима, `MovieCard`, loading/empty/error/offline состояния. Компоненты принимают state/callback, не вызывают API и не знают навигацию. Добавить контентные описания, корректную работу длинного названия, null-постера и увеличенного шрифта. Русские строки вынести в resources.

**Выход:** каталог Compose previews и одна эталонная stateless Screen + ViewModel + Fake. **Приёмка:** владельцы могут сверстать свои экраны без новых базовых компонентов; карточка корректна на узком экране, с длинным текстом и без картинки. Проверить клавиатуру/системные отступы на устройстве. Пока точного экспорта нет, пометить визуальную приёмку как незавершённую, но не задерживать логику.

## D1-03 Оболочка поиска и навигация

**UC:** общий каркас UC-01/07/08/09 и возврат UC-02/04. **Экраны:** 2.1, 2.1а, 2.1б, 2.8, 3.1–3.5а в применимой части. **Модули:** `search`, `search-api`, `app`; прямых HTTP-запросов в оболочке нет.

Подключить четыре `SearchModalityUi`, фиксированный порядок режимов и UI авторизации. Создать временные stub-входы, которые остальные владельцы заменяют в своих модулях. Зафиксировать `SearchCompletion` и правило однократной записи истории. Общие found/empty/wrong film состояния должны возвращать в нужный режим без потери черновика, если он ещё доступен.

Сделать `PendingActionStore`, typed routes, `SearchResultStore`; из гостевого защищённого действия идти на login и возвращаться по ID. Не передавать список фильмов, пароль или media bytes в маршрут. Сохранять результаты при повороте; при уничтожении процесса предлагать восстановление по истории или повтор, а не пустой сломанный экран.

**Фейки:** Session guest/auth/expired, completion с 10/1/0 результатами, HistoryRepository с ошибкой записи. **Приёмка:** каждый режим подключается без изменения оболочки; в гостевом TEXT нет запроса сессии ради поиска; protected mode предлагает login; cancel login возвращает в исходное место; два одинаковых completion не создают две записи/два экрана; ошибка истории не скрывает результат. Тесты ViewModel и один UI smoke навигации.

## D1-04 Текст и выдача

**UC-01, FR-01/02/04. Экраны:** 2.1а, 2.2, 2.8, 3.2, 3.2а, 3.5, 3.5а. **API:** `POST /search/text`, JSON `query`, ответ `SearchResponse.results`. **Модуль:** `search-text`; общая выдача в `search`.

Сделать поле 3–250 символов, очистку, счётчик и submit. Код backend подтверждает trim Unicode White_Space и длину в Unicode code points; не использовать Kotlin String.length как число символов для surrogate pairs. Проверить границы, emoji и Unicode-пробелы в контрактном тесте. Реализовать Fake и Retrofit adapter с mapper. Гость получает до 10 результатов в серверном порядке; первый можно отметить как лучшее совпадение, числовую уверенность не показывать.

**Ранний шаг D2:** ещё до готового UI отправить контрольный запрос к стенду и сохранить обезличенный fixture. Это часть этой задачи, а не ожидание D4. **Приёмка:** 2/3/250/251 символ, пустой/пробельный ввод, русский/английский текст; один submit при повторных нажатиях; success/empty/offline/503/429; отменённый или старый ответ не заменяет новый; выбор фильма открывает MovieRoute с правильным ID. Контрактный тест проверяет отсутствующие nullable поля и неизвестные дополнительные поля согласно принятой схеме.

## D1-05 Карточка фильма

**UC-02 частично; интеграция UC-11/13. Экраны:** 3.1, 3.2, 4.1, 4.1а, 4.2, 4.6. **API владельца:** `GET /movies/{movie_id}`, `GET /movies/{movie_id}/rating-summary`. **Модуль:** `movies`. **Чужой контракт:** PersonalMoviesRepository Dev 2; его методы реализуются только у Dev 2.

Показать название, оригинальное название, год, постер, возраст, длительность, жанры/страны, описание, актёров/создателей, среднюю оценку и число оценок. Обязательные в выбранной схеме поля проверять контрактными тестами; null/пустые списки имеют нормальное представление. Отдельная ошибка rating summary не скрывает загруженную карточку; отсутствующий endpoint нельзя представить как «0 оценок».

Кнопки watchlist/watched и рейтинг обращаются к общему personal contract. Гостевое нажатие сохраняет конкретное действие перед login. Отзывов/реакций в первой версии нет. После изменения оценки обновить summary; после изменения списков состояние одновременно обновляется в карточке и библиотеке.

**Фейки:** полный фильм, неполные метаданные, 404, пустой cast, недоступный summary; personal state с двумя независимыми отметками. **Приёмка:** переход из всех четырёх режимов/истории/списка работает; back возвращает прежнюю выдачу; карточка доступна гостю; private state не запрашивается гостем; после login нужное действие выполняется один раз; оценка отсутствует как null, не как 0. Тест mapper и ViewModel; ручная сверка экранов.

## D1-06 Интеграция и восстановление

Собрать реальные entrypoints Dev 2–4, заменить согласованные stubs и проверить demo/prod DI. Проверить смену режима во время загрузки, повторное открытие карточки, logout с открытой библиотекой, одновременные 401, возврат после отмены входа, поворот и пересоздание Activity.

**Выход:** единый APK к концу D8 и список оставшихся дефектов. **Приёмка:** нет импорта реализации feature из другой feature; нет дублирующихся маршрутов или двух UI-обработчиков одного события; пять сквозных сценариев из [приёмки](acceptance.md) проходят. Фиксировать backend-блокеры отдельно от мобильных багов.

## Передачи и следующие задачи

В D1 передайте Dev 2–4 контракт режима и routes; в D2 — компоненты и пример экрана. Примите от Dev 2 personal Fake, от Dev 3 history Fake, от Dev 4 session Fake. Каждый контракт проверьте на одном потребительском тесте до завершения UI.

D9–D10: ваши 12 ч идут на навигацию и сквозные ошибки; новые функции не брать. После MVP: карточка отзывов/сортировки/пагинация, интеграция редактора отзывов, дальнейшие маршруты и общие компоненты — задачи P2-04 и интеграция этапа 2.
