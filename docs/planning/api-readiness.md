# Готовность API для мобильного DejaView

Обновлено 21 ноября 2026 года: проверены не только два Swagger, но и обработчики backend. [Доказательства по исходникам](backend-evidence.md) подтверждают 24 реализованные API-операции; тесты найдены, но не запускались. **Приложенный Swagger 1.4.1 — целевая спецификация мобильного плана, но не подтверждённая реализация сервера.** Обезличенные снимки сохранены рядом; они не являются побайтовыми оригиналами. Сравнение путей не заменяет проверку backend на стенде.

| Источник | Версия | Операций HTTP | Статус для плана |
| --- | --- | --- | --- |
| [Приложенный Swagger](sources/mobile-proposal-1.4.1.yaml) | 1.4.1 | 51 | Целевые методы и DTO |
| [Снимок public main](sources/upstream-openapi-2026-11-20.yaml) | 0.0.1 | 24 | Фактический опубликованный контракт на момент загрузки |

Общих пар method/path — 20. Только в приложенном — 31; только в public main — 4. Это не «31 нереализованный endpoint»: часть функций может существовать иначе или в ещё не опубликованной ветке. **Готовность runtime не проверена**, так как production/staging URL и тестовая учётная запись не предоставлены. [Официальный контракт проекта](https://github.com/dejaview-nsu/dejaview-docs/blob/main/api/openapi.yaml).

## Различия, влияющие на независимую работу

| Область | Мобильный 1.4.1 | Public main в снимке | Следствие |
| --- | --- | --- | --- |
| Чтение списков | `/users/me/watchlist`, `/users/me/watched` | `/users/me/lists/{list_type}` | Dev 2 нужен явный выбор адаптера |
| Изменение списков | Отдельные watchlist/watched пути с movie_id | `/users/me/lists/{list_type}/{movie_id}` | Нельзя просто заменить base URL |
| Форма ответа списка | `items,page,total_pages,total_items` | `movies,total` | Разные DTO и mapping пагинации |
| Мои отметки | `/movies/{movie_id}/my-state`: in_watchlist/is_watched/my_rating и др. | `/users/me/movies/{movie_id}`: want_to_watch/watched | Старый state не даёт личную оценку |
| Оценки | my-rating PUT/DELETE, rating-summary GET | Нет маршрутов в проверенном backend main | Обязательная внешняя зависимость MVP |
| Профиль/статистика | `/users/me`, statistics/actions/ratings/reviews/avatar | Нет маршрутов в проверенном backend main | Минимальный профиль MVP берёт данные из session |
| Отзывы | Чтение + создание/изменение/удаление + реакции | Есть чтение `/movies/{movie_id}/reviews`, нет соответствующих mutation paths | Полная работа с отзывами требует backend этапа 2 |
| Мобильный OIDC | `POST /auth/oidc/exchange` | Нет mobile exchange в backend; browser OIDC реализован | Custom Tabs сами не передают cookie в native HTTP; требуется exchange |
| Биллинг | Пять операций, включая entitlement/webhook | Нет маршрутов в проверенном backend main | Отдельный этап 3; webhook не вызывает Android |

Поиск всех четырёх модальностей, login/session/logout и карточка представлены в обоих контрактах, но совместимость ответов и реальных файлов нужно проверить. В загруженном public main уже есть M4A в audio и actors в MovieCard; считать их отсутствующими по устаревшему описанию README нельзя.

## Решение по совместимости на D2

Dev 2 начинает со сверки существующих обработчиков и адаптера списков текущего main. Для 18 целевых операций MVP восемь имеют точную пару method/path, семь операций membership/списков покрываются существующими аналогами с другими DTO, три операции оценки требуют отдельного решения backend. Не ставить задачу повторно реализовать все 18 операций. Согласованный контракт хранится как отдельный выбранный baseline с hash; приложенный источник не переписывается задним числом.

UI/domain одинаковы для адаптеров. Нельзя пробовать разные paths до первого 200, выводить `my_rating=0` при отсутствии поля или подставлять Fake после 404. Endpoint, отсутствующий по согласованному плану, — зависимость и блокер соответствующей реальной функции.

Полный [каталог 51 операции](api-inventory.md) содержит владельца, этап, operationId, UC и наличие method/path в снимке. Это перечень контрактов, не перечень проверенных endpoint.

По удалению аккаунта конкретные UC-18 и DELETE `/users/me` согласуются: оценки/отзывы остаются без автора. Общее описание «персональные данные удаляются» не означает, что Android должен сам удалять серверные отзывы. Очистку локальных данных реализует клиент, а серверную анонимизацию проверяют отдельным интеграционным сценарием этапа 2.

## Реестр проверки стенда

На D2 каждый владелец заполняет результат своей операции: build стенда, время, HTTP status, ожидаемая/полученная схема, ссылка на обезличенный fixture, решение по несовпадению. Достаточно одного реального успеха и существенных отрицательных случаев; отсутствие результата называется «не проверено», а не «готово». CI использует локальные fixtures/MockWebServer, live smoke запускается отдельно.

Контрактные ошибки разделяются: **нет в спецификации**, **есть в спецификации, не подтверждено на стенде**, **стенд нарушает согласованную схему**, **ошибка клиента**. Это позволяет каждому разработчику продолжать свою часть без ложного закрытия задачи.
